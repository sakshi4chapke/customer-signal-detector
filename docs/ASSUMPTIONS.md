# Assumptions & Data Notes

## 1. Data source

Synthetic dataset generated by `src/data_generator.py` with a fixed random
seed (42), making the dataset fully reproducible. The POC brief explicitly
permits generated data: *"Candidates are free to use any publicly available
dataset or generate a suitable dataset using AI tools."*

| File | Rows | Purpose |
|---|---|---|
| `data/raw/customers.csv` | 203 (200 unique + 3 planted duplicates) | Structured behavioural + billing data |
| `data/raw/conversations.csv` | 487 | Multi-turn support transcripts (LLM input) |
| `data/raw/answer_key.csv` | 200 | Ground-truth labels — **evaluation only** |
| `data/raw/data_dictionary.csv` | 31 | Column definitions and the signal each feeds |

## 2. Six planted archetypes

Rather than generating random values, six customer "recipes" were designed
with deliberately different signal profiles, so the detection logic has real
structure to find and can be measured against a known answer.

| Archetype | Count | Design intent |
|---|---|---|
| healthy_loyal | 70 | Baseline — should score Low |
| quiet_drifter | 30 | Behavioural risk, near-zero text signal |
| loud_but_stable | 30 | Strong negative text, healthy behaviour |
| billing_wounded | 30 | Payment failures and billing disputes |
| escalating_churner | 24 | Explicit exit intent — should score Critical |
| new_fragile | 16 | Poor onboarding, short tenure |

### Verified separation (means per archetype)

| Archetype | Days inactive | Usage change | Tickets | Failed payments | Churned |
|---|---|---|---|---|---|
| healthy_loyal | 2.0 | +9.8% | 1.2 | 0.0 | 0% |
| loud_but_stable | 1.8 | +8.5% | 6.4 | 0.0 | 10% |
| new_fragile | 13.5 | −24.7% | 2.6 | 0.5 | 30% |
| billing_wounded | 9.5 | −13.5% | 4.0 | 1.9 | 60% |
| escalating_churner | 30.8 | −72.9% | 8.0 | 1.1 | 100% |
| **quiet_drifter** | **57.3** | **−66.4%** | **0.6** | **0.0** | **70%** |

## 3. The two adversarial cases

These exist specifically to test whether the system genuinely correlates
multiple signals or merely performs sentiment analysis.

**quiet_drifter** — 57 days since last login, usage down 66%, NPS never
answered, and only 0.6 support tickets. Their transcripts are mundane
("Password reset link isnt arriving… got it thanks"). Yet 70% churn. A
support-ticket- or sentiment-driven system never surfaces them.

**loud_but_stable** — 6.4 tickets per quarter and visibly irritated language,
but they log in daily, usage is growing, and they pay on time. Only 10% churn.
A sentiment-only system ranks them as the highest risk in the book.

**Conclusion drawn:** anger indicates engagement; silence indicates exit.
The system must weight behavioural inactivity at least as heavily as negative
sentiment. If the pipeline ranks quiet_drifter above loud_but_stable,
multi-signal correlation is demonstrably doing work.

### A second discriminator: unresolved ratio

Ticket *volume* alone cannot separate a vocal loyal customer from a departing
one — both complain frequently. Resolution *rate* can:

| Archetype | Tickets | Unresolved | Ratio | Churned |
|---|---|---|---|---|
| loud_but_stable | 6.4 | 0.8 | 13% | 10% |
| escalating_churner | 8.0 | 5.5 | 69% | 100% |

A customer who complains and gets fixed stays. A customer who complains and
is ignored leaves. `unresolved_tickets_90d` was added to capture this.

## 4. Data quality issues (deliberately injected)

Real operational data is messy; the pipeline must survive it. Issues were
planted so the cleaning stage has genuine work and can produce a
before/after quality report.

| Issue | Observed | Handling decision (Phase 3) |
|---|---|---|
| Duplicate customer rows | 3 | Drop, keep first occurrence |
| Negative `tenure_months` | min = −45 | Invalid → clip to 0 and flag |
| `nps_score` = 47 (valid 0–10) | max = 47 | Invalid → set null |
| `csat_avg` = 9.9 (valid 1–5) | max = 9.9 | Invalid → set null |
| Missing `csat_avg` | 46 | Keep null — do not impute |
| Missing `nps_score` | 31 | Keep null — becomes NPS_SILENCE signal |
| Missing `avg_resolution_hours` | 10 | Impute with median |
| Missing `region` | 6 | Fill "Unknown" |
| Inconsistent `segment` casing | 21 rows lowercased | Normalise to title case |
| Whitespace padding in `plan_tier` | ~12 rows | Strip |

## 5. Key modelling assumptions

**1. Missing NPS is a signal, not a gap.**
A customer who never responded to the satisfaction survey is not "average" —
non-response correlates with disengagement. Imputing the mean would erase the
signal entirely. Missing NPS therefore produces a low-severity NPS_SILENCE
signal rather than a filled value.

**2. Missing CSAT is not imputed either**, for the same reason. Only
`avg_resolution_hours` is median-imputed, because its absence reflects a
logging gap rather than customer behaviour.

**3. 31 customers have zero conversations.**
This is realistic and meaningful — they receive a NO_CONTACT signal. It
requires a LEFT JOIN during aggregation; an inner join would silently drop
these customers, and they are disproportionately quiet drifters, the
highest-risk group. The design anticipates this.

**4. Absolute thresholds are used** (e.g. 30 days inactive = risk).
Production should use per-customer relative baselines, since an enterprise
administrator logging in monthly may be entirely normal behaviour. One
relative signal (`usage_pct_change_30d`) is implemented to demonstrate the
approach.

**5. Target leakage was identified and corrected.**
`churned_flag` was initially written into `customers.csv`, meaning the
pipeline's input file contained the answer. It now lives only in
`answer_key.csv`, which is read exclusively by the Phase 12 evaluation
script. No scoring component has access to it.

**6. Transcripts never contain the word "churn".**
Real customers say "we're already trialling an alternative platform" or
"send me the offboarding process". Detecting an explicit keyword would be
string matching, not signal detection.

**7. Conversation timestamps are exponentially distributed** toward the
present, mirroring a real support queue. This makes recency weighting
meaningful in aggregation.

**8. Revenue is correlated with segment** (Enterprise $4k–20k, Startup
$60–500) so that "revenue at risk" is a realistic operational metric rather
than a random number.

## 6. Limitations

- Patterns are self-planted, so Phase 12 metrics validate that the detection
  logic behaves **as designed**. They are not a claim of real-world predictive
  accuracy, which would require historical churn outcomes.
- 200 customers is small. Sufficient to demonstrate ranking behaviour; too
  small to fit or validate a trained model.
- Transcripts are drawn from a template pool, so linguistic variety is lower
  than real support logs. The LLM extraction stage is therefore likely to
  perform better here than it would in production.
- No time-series history: each customer is a single snapshot, so trend
  detection over multiple periods is out of scope for this POC.
